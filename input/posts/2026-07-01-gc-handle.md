2024 and 2025 were big years for GC handles in the CoreCLR garbage collector. We have new public interfaces
for working with GC handles. And for the first time in over 13 years, new types of GC handles handles
have been introduced to the CoreCLR GC. The former you may be able to use in your own applications
and libraries. The later are implementation details of the CoreCLR runtime that you can't directly use
but are fascinating.

## Background

I previously covered CoreCLR GC handles in my 2024 post, where I discussed the 10 different types of GC handles implemented in CoreCLR's garbage
collector. To summarize, the GC in CoreCLR is a
[tracing garbage collector](https://en.wikipedia.org/wiki/Tracing_garbage_collection),
which means the GC determines which objects are alive by walking the object graph, starting at static
variables and local variables[^1]. Not all code patterns fit into this model, particularly cases
involving interop with native code. When it is not possible to express object lifetimes though the normal
system, the GC Handle abstraction provides a way to explicitly control and track object lifetimes.

## New Public APIs

Since the dawn of .NET, the
[`GCHandle` struct](https://learn.microsoft.com/dotnet/api/system.runtime.interopservices.gchandle)
has been the main way of interacting with GC handles. .NET 6 added
[`DependentHandle` struct](https://learn.microsoft.com/dotnet/api/system.runtime.dependenthandle).

.NET 10 [added](https://github.com/dotnet/runtime/issues/94134) 4 new structs
and classes for using GC handles. Compared to the old `GCHandle` struct, these have better type safety
via by using generic types and by using different structs for different types of handles. They also
have slightly better performance.

* [`GCHandle<T>`](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.gchandle-1) -
  a strong GC handle. This replaces using `GCHandleType.Normal` with the old `GCHandle`.
* [`WeakGCHandle<T>`](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.weakgchandle-1) -
  a weak GC handle. This replaces using `GCHandleType.Weak` or `GCHandleType.WeakTrackResurrection`
  with the old `GCHandle`.
* [`PinnedGCHandle<T>`](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.pinnedgchandle-1) -
  a GC handle that pins its object. This replaces using `GCHandleType.Pinned` with the old `GCHandle`.
* [`GCHandleExtensions`](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.gchandleextensions) -
  this adds extension methods to `PinnedGCHandle<T>` for getting pointers to pinned arrays and strings.

I wrote a micro benchmark to illiterate that performance difference.
The extra indirections and `MethodImplOptions.NoInlining` are for the benefit of the the dissembly
we will look at after the results.

```csharp
using System.Runtime.CompilerServices;
using System.Runtime.InteropServices;
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

BenchmarkRunner.Run<MyBenchmarks>(args: args);

[StructLayout(LayoutKind.Sequential)]
public class IntBox
{
    public int SomeInt;
}

[DisassemblyDiagnoser]
public class MyBenchmarks
{
    private static readonly GCHandle s_standardHandle = GCHandle.Alloc(new IntBox(), GCHandleType.Pinned);
    private static readonly PinnedGCHandle<IntBox> s_newHandle = new PinnedGCHandle<IntBox>(new IntBox());

    [MethodImpl(MethodImplOptions.NoInlining)]
    IntBox StandardGcHandle(GCHandle hand) => (IntBox)hand.Target!;

    [Benchmark(Baseline = true)]
    public IntBox StandardGcHandle() => StandardGcHandle(s_standardHandle);

    [MethodImpl(MethodImplOptions.NoInlining)]
    IntBox NewGcHandle(PinnedGCHandle<IntBox> hand) => hand.Target;

    [Benchmark]
    public IntBox NewGcHandle() => NewGcHandle(s_newHandle);
}
```

When I run this benchmark on my computer using .NET 10.0.9,
the new GC handle takes 82% of the time to run compared to the old GC handle:

| Method           | Mean      | Error     | StdDev    | Ratio | RatioSD | Code Size |
|----------------- |----------:|----------:|----------:|------:|--------:|----------:|
| StandardGcHandle | 1.1609 ns | 0.0569 ns | 0.0559 ns |  1.00 |    0.06 |      71 B |
| NewGcHandle      | 0.9536 ns | 0.0219 ns | 0.0171 ns |  0.82 |    0.04 |      20 B |

The code generated for the new handle is very simple; it merely derefernces the handle:

```assembly
; MyBenchmarks.NewGcHandle(System.Runtime.InteropServices.PinnedGCHandle`1<IntBox>)
       mov       rax,[rsi]
       ret
; Total bytes of code 4
```

Compare that to the old GC handle, which has a lot of extra checks:

```assembly
; MyBenchmarks.StandardGcHandle(System.Runtime.InteropServices.GCHandle)
       push      rbp
       mov       rbp,rsp
       // Test for a zero handle value and throw `InvalidOperationException` if zero.
       test      rsi,rsi
       je        short M01_L01
       // Clear IsPinned bit from the bottom of the handle value.
       and       rsi,0FFFFFFFFFFFFFFFE
       // Dereference handle value.
       mov       rsi,[rsi]
       mov       rax,rsi
       // Check for null and return early if null.
       test      rax,rax
       je        short M01_L00
       // Check if the object is an instance of IntBox and branch to fallback more complicated
       // casting logic if it is not an exact match.
       mov       rdi,offset MT_IntBox
       cmp       [rax],rdi
       jne       short M01_L02
       // Now that we have performed all the checks, we can return the handle value.
M01_L00:
       pop       rbp
       ret
M01_L01:
       call      qword ptr [7FB1E12CD860]
       int       3
M01_L02:
       call      System.Runtime.CompilerServices.CastHelpers.ChkCastClass(Void*, System.Object)
       jmp       short M01_L00
; Total bytes of code 55
```

## New internal GC handle types

When CoreCLR was open sourced in 2015, its GC has supported 10 handles types.
See my [previous post](2024-03-31-gc-handle.md) or the
[original source code](https://github.com/dotnet/runtime/blob/2024b63acd460edeb53b2ce6984710ab51c11f2f/src/coreclr/src/gc/objecthandle.h)
for more details

In 2024 and 2025 two new types of GC handles were added.

## Weak Interior Pointer Handles

.NET 9 added the weak interior pointer handles (`HNDTYPE_WEAK_INTERIOR_POINTER`). These handles have
an extra pointer value associated with them. It is a pointer to a location in memory than contains
the extra to object. The pointer to the object may be to the beginning of the object or to a location
in the interior of the object. Whenever the object is moved, location pointed to by the associated
pointer is updated to compensate.

This diagram shows how this are laid out in memory. Initially the handle is created to point to the
object and location in memory that points to the interior of the object. Whenever the GC moves the
object, the GC handle is updated to point to the new location and the Interior pointer in unmanaged
memory is updated.

```
                                     Object in GC heap                          
   GC Handle                                                            
                                                                     
┌────────────────────────────┐       ┌──────────────┐                
│  Primary handle value      ├──────►│Method Table  │                
│                            │       │              │                
┼────────────────────────────┤       ├──────────────┤                
│                            │       │Field 1       │◄──────────────┐
│  Secondary pointer value   ├──┐    │              │               │
│                            │  │    ├──────────────┤               │
└────────────────────────────┘  │    │Field 2       │               │
                                │    └──────────────┘               │
                                │                                   │
                                │                                   │
                                │     Unmanaged or pinned memory    │
                                │                                   │
                                │    ┌───────────────────┐          │
                                │    │...                │          │
                                │    ├───────────────────│          │
                                └───►│Interior Pointer   ├──────────┘
                                     ├───────────────────┤           
                                     │...                │           
                                     └───────────────────┘           
```

This handle type was added in [pull request #100446](https://github.com/dotnet/runtime/pull/100446).
They were initially used to keep a pointer to the managed `System.Type` object for collectable types
updated in the unmanaged `MethodTable` and `MethodDesc` data structures.

[Pull request #99183](https://github.com/dotnet/runtime/pull/99183) changed how memory for static
variables is allocated (and freed for collectable assemblies). It made the code for managing this
memory simpler and accessing this memory more performant. The weak interior pointer handle is used
when allocating memory for static variables in collectable assemblies. See the PR description and
[the Book of the Runtime section on static variables](https://github.com/dotnet/runtime/blob/main/docs/design/coreclr/botr/type-system.md#static-variables).
