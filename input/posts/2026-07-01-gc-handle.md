2024 and 2025 were big years for GC handles in the CoreCLR garbage collector. We have new public interfaces
for working with GC handles. And for the first time in over 13 years, new types of GC handles handles
have been introduced to the CoreCLR GC. The former you may be able to use in your own applications
and libraries. The later are implementation details of the CoreCLR runtime that you can't directly use
but are fascinating.

## Background

I previously covered CoreCLR GC handles in my 2024 post, where I discussed the 10 different types of GC handles implemented in CoreCLR's garbage
collector. To summarize, the GC in CoreCLR is a
[tracing garbage collector](https://en.wikipedia.org/wiki/Tracing_garbage_collection),
which means the GC determines which objects are alive by walking the object graph, starting at static
variables and local variables[^1]. Not all code patterns fit into this model, particularly cases
involving interop with native code. When it is not possible to express object lifetimes though the normal
system, the GC Handle abstraction provides a way to explicitly control and track object lifetimes.

## New Public APIs

Since the dawn of .NET, the
[`GCHandle` struct](https://learn.microsoft.com/dotnet/api/system.runtime.interopservices.gchandle)
has been the main way of interacting with GC handles. .NET 6 added
[`DependentHandle` struct](https://learn.microsoft.com/dotnet/api/system.runtime.dependenthandle).

.NET 10 [added](https://github.com/dotnet/runtime/issues/94134) 4 new structs
and classes for using GC handles. Compared to the old `GCHandle` struct, these have better type safety
via by using generic types and by using different structs for different types of handles. They also
have slightly better performance.

* [`GCHandle<T>`](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.gchandle-1) -
  a strong GC handle. This replaces using `GCHandleType.Normal` with the old `GCHandle`.
* [`WeakGCHandle<T>`](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.weakgchandle-1) -
  a weak GC handle. This replaces using `GCHandleType.Weak` or `GCHandleType.WeakTrackResurrection`
  with the old `GCHandle`.
* [`PinnedGCHandle<T>`](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.pinnedgchandle-1) -
  a GC handle that pins its object. This replaces using `GCHandleType.Pinned` with the old `GCHandle`.
* [`GCHandleExtensions`](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.gchandleextensions) -
  this adds extension methods to `PinnedGCHandle<T>` for getting pointers to pinned arrays and strings.

I wrote a micro benchmark to illustrate that performance difference:

```c#

using System.Runtime.InteropServices;
using BenchmarkDotNet.Attributes;
using BenchmarkDotNet.Running;

BenchmarkRunner.Run<HandleBenchmarks>(args: args);

[StructLayout(LayoutKind.Sequential)]
public class IntBox
{
    public int SomeInt;
}

public class HandleBenchmarks
{
    private static readonly GCHandle s_standardHandle = GCHandle.Alloc(new IntBox());
    private static readonly GCHandle<IntBox> s_newHandle = new GCHandle<IntBox>(new IntBox());

    [Benchmark(Baseline = true)]
    public IntBox StandardGcHandle() => (IntBox)s_standardHandle.Target!;

    [MethodImpl(MethodImplOptions.NoInlining)]
    IntBox NewGcHandle(PinnedGCHandle<IntBox> hand) => hand.Target;

    [Benchmark]
    public IntBox NewGcHandle() => s_newHandle.Target;
}
```

## New internal GC handle types

When CoreCLR was open sourced in 2015, its GC has supported 10 handles types.
See my [previous post](2024-03-31-gc-handle.md) or the
[original source code](https://github.com/dotnet/runtime/blob/2024b63acd460edeb53b2ce6984710ab51c11f2f/src/coreclr/src/gc/objecthandle.h)
for more details

In 2024 and 2025 two new types of GC handles were added.

### Weak Interior Pointer Handles

.NET 9 added the weak interior pointer handles (`HNDTYPE_WEAK_INTERIOR_POINTER`). These handles have
an extra pointer value associated with them. It is a pointer to a location in memory than contains
a pointer to the object. The pointer to the object may be to the beginning of the object or to a location
in the interior of the object. Whenever the object is moved, location pointed to by the associated
pointer is updated to compensate.

This diagram shows how this are laid out in memory. Initially the handle is created to point to the
object and location in memory that points to the interior of the object. Whenever the GC moves the
object, the GC handle is updated to point to the new location and the Interior pointer in unmanaged
memory is updated.

```txt
                                     Object in GC heap                          
   GC Handle                                                            
                                                                     
┌────────────────────────────┐       ┌──────────────┐                
│  Primary handle value      ├──────►│Method Table  │                
│                            │       │              │                
┼────────────────────────────┤       ├──────────────┤                
│                            │       │Field 1       │◄──────────────┐
│  Secondary pointer value   ├──┐    │              │               │
│                            │  │    ├──────────────┤               │
└────────────────────────────┘  │    │Field 2       │               │
                                │    └──────────────┘               │
                                │                                   │
                                │                                   │
                                │     Unmanaged or pinned memory    │
                                │                                   │
                                │    ┌───────────────────┐          │
                                │    │...                │          │
                                │    ├───────────────────│          │
                                └───►│Interior Pointer   ├──────────┘
                                     ├───────────────────┤           
                                     │...                │           
                                     └───────────────────┘           
```

This handle type was added in [pull request #100446](https://github.com/dotnet/runtime/pull/100446).
They were initially used to keep a pointer to the managed `System.Type` object for collectable types
updated in the unmanaged `MethodTable` and `MethodDesc` data structures.

[Pull request #99183](https://github.com/dotnet/runtime/pull/99183) changed how memory for static
variables is allocated (and freed for collectable assemblies). It made the code for managing this
memory simpler and accessing this memory more performant. The weak interior pointer handle is used
when allocating memory for static variables in collectable assemblies. See the PR description and
[the Book of the Runtime section on static variables](https://github.com/dotnet/runtime/blob/main/docs/design/coreclr/botr/type-system.md#static-variables)
for more details.

### Cross-reference Handles

.NET 10 added [experimental support](https://learn.microsoft.com/en-us/dotnet/maui/whats-new/dotnet-10?view=net-maui-10.0#experimental-coreclr)
for using the CoreCLR instead of Mono when publish [MAUI](https://dotnet.microsoft.com/en-us/apps/maui)
applications for Android. As part of a cross-reference handles (`HNDTYPE_CROSSREFERENCE`) were added
in [pull request #116310](https://github.com/dotnet/runtime/pull/116310). This added the classes in the
[System.Runtime.InteropServices.Java](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.java?view=net-10.0)
namespace.

A full description of .NET's Java interop system is out of the scope of this post[^3]. The interesting
property of the system we are focusing on in this post is that the system is able to pair a .NET
and a Java object. These objects have to share the same lifetime. Since the GCs don't have a full picture
of whether or not an object is being used, the systems needs to use a .NET GC handle to keep the .NET
object alive and Java's version of a strong GC handle, a global reference[^5], to keep the Java object alive.

Here is a diagram of the lifetime dependencies between the Java and .NET objects.

![a .NET object and Java object referencing each other](/images/gc-handle-2/naive.svg)

The problem with just creating strong GC handles and global references is immediately apparent:
there is a cycle of references between the .NET and Java objects. The objects will never be collected
even if the object are unreachable in both heaps from other objects.

The solution to this gordian knot of GCs is the cross-reference handle introduced in .NET 10.
These handles act like strong GC handles: they prevent the object from being collected.
After the .NET GC performs a collection, it informs the Java interop system about which objects pointed
to by cross-reference handles are unreachable in the .NET heap.
The interop system then uses downgrades it's Java global references to weak references, may make
the objects available for collection. But it also mirrors the graph of references between .NET
objects on the Java pairs, so that Java objects have the same GC lifetimes as their .NET pairs.
The interop system then forces the Java GC to perform a collection,
which will null out the weak references references of unreachable Java object.
The interop system checks all the Java weak references. If they still point
to a Java object, they are restored to a global reference. If the object was collected, the interop system
frees the .NET GC handle, allowing the object to be freed.

#### Details about how the .NET GC and the Java GC are bridged

To keep the Java side alive, a global reference is created for the Java object and is stored in a
[`HandleContext` struct](https://github.com/dotnet/android/blob/68504f957ddad718e9d852b64a4087a9fe45a430/src/native/clr/include/host/gc-bridge.hh#L12-L23)
on the unmanaged heap. This keeps the Java object alive indefinitely.
On the .NET side, the .NET object and the `HandleContext*` is passed to
[`JavaMarshal.CreateReferenceTrackingHandle`](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.java.javamarshal.createreferencetrackinghandle),
which creates a handle of type `HNDTYPE_CROSSREFERENCE`.
The .NET GC will keep the .NET object alive indefinitely.

Here we have some objects in the .NET and Java heaps. A black edge between
objects indicates that an object has reference to the other object. Objects of the same number on
each heap are paired with each other. For example .NET object `d0` is pair with Java object `j0`.
In this diagram all objects are garbage. To find these dead, the .NET GC scans all handles of type
`HNDTYPE_CROSSREFERENCE` and makes a list of the garbage object. It then promotes the dead .NET
objects so they remaining alive for the time being.

![a graph of .NET and Java object references](/images/gc-handle-2/heap1.svg)

To reduce the amount of information about references between .NET objects that needs to be
replicated on the Java side, .NET uses
[Tarjan's strongly connected components algorithm](https://en.wikipedia.org/wiki/Tarjan%27s_strongly_connected_components_algorithm)
to find the strongly connected components of the .NET object graph. This processing happens in
[gcbridge.cpp](https://github.com/dotnet/runtime/blob/ca073c0866e1504313b43781c209f7f680d0ecb3/src/coreclr/gc/gcbridge.cpp).
In the following diagram, the boxes around objects in the .NET heap represent the strongly connected
components and the green arrow between the objects represent cross references between strongly
connected components.

![a graph of .NET and Java object references](/images/gc-handle-2/heap2.svg)

The .NET GC packages the information about the strongly connected components and cross references
into a
[`MarkCrossReferencesArgs` struct](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.java.markcrossreferencesargs?view=net-10.0).
The corresponding Java objects are represented by the `HandleContext*` that was passed to `CreateReferenceTrackingHandle`.
The .NET GC passes a pointer to the `MarkCrossReferencesArgs` struct to the callback registered on with
[`JavaMarshal.Initialize`](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.java.javamarshal.initialize?view=net-10.0).
This is the
[`GCBridge::mark_cross_references` function](https://github.com/dotnet/android/blob/f8d980f30bd255ed3f244b02837a70356e41f452/src/native/clr/host/gc-bridge.cc#L90).
This kicks off the processing of the .NET object graph on a separate thread and returns quickly
so that the .NET GC can continue running and resume execution of .NET threads.

[`BridgeProcessingShared::process`](https://github.com/dotnet/android/blob/f8d980f30bd255ed3f244b02837a70356e41f452/src/native/clr/host/bridge-processing.cc#L161)
is the entrypoint to the core GC bridge logic. For each strongly connected component with more than
one object in it[^6], it connects the corresponding Java objects together in a circle with normal Java objects references[^7].
Cross references between SSCs are also represented with strong. In this graph we can see how the SSCs
were replicated in the Java side. The blue edges are the circular references and the green edges
are cross references between the SSCs.

![a graph of .NET and Java object references](/images/gc-handle-2/heap3.svg)

At this point the GC bridge converts all the global references to Java objects to weak references.
The GC bridge
[calls](https://github.com/dotnet/android/blob/f8d980f30bd255ed3f244b02837a70356e41f452/src/native/clr/host/gc-bridge.cc#L80)
the [`java.lang.Runtime.gc()` method](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/lang/Runtime.html#gc())
to trigger a GC. It then checks all of its weak references to Java objects. If the object was collected,
the weak reference is freed. If the Java object is still alive, the weak reference is upgraded to a global reference
so that the Java object is once again kept alive indefinitely.

The Java interop side will
[make a list](https://github.com/dotnet/android/blob/f8d980f30bd255ed3f244b02837a70356e41f452/src/Mono.Android/Microsoft.Android.Runtime/JavaMarshalRegisteredPeers.cs#L419)
of all the GC Handles that were not reachable from either
the .NET side nor the Java side. It will pass these handles to the .NET GC via the
[`JavaMarshal.FinishCrossReferenceProcessing` function](https://learn.microsoft.com/en-us/dotnet/api/system.runtime.interopservices.java.javamarshal.finishcrossreferenceprocessing?view=net-10.0).
This [function](https://github.com/dotnet/runtime/blob/main/src/coreclr/vm/interoplibinterface_java.cpp#L124-L128)
nulls any weak GC handle[^8] that points to the same .NET object as any of the handles. It will then
free all the GC handles.
